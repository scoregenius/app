01  Executive summaryScoreGenius

What was done, and why it matters

ScoreGenius had a refreshed brand but an interior that predated it. This programme closed that gap — not by restyling, but by establishing a design system, rebuilding the core screen around the product's actual job, and auditing what was already shipping.

3Screens specified across three sports
18Defects found, 14 already fixed
7Commits, shipped in sequence
0New dependencies or API changes

The problem

The Games screen presents twelve to fifteen prediction cards on a typical day. Every card carried the same visual weight, which meant a user had to read all fifteen to find the two worth acting on. The product's own output — the predicted score and the market edge — were among the quietest elements on screen: the edge rendered as muted grey text, the prediction at 13 pixels.

The response

The card was restructured from a list of facts into a matchup: one row per team, each carrying that team's predicted score in a fixed, right-aligned column, with the model's pick held at full contrast and the other side receded. A reader now scans a full slate by running their eye down a single column. The market edge — the rarest and most valuable signal — became the loudest element, encoded in colour, border and a card-edge rail rather than in words alone.

What else it surfaced

Documenting the system required auditing what existed. That audit found eighteen defects, several shipping to users: cards turning transparent on hover in light mode, an invisible white-on-white heading, placeholder zeros presented as real betting lines, and domed baseball stadiums reporting outdoor weather. Fourteen are now fixed; the four remaining sit on screens the redesign has not reached yet and are scheduled with them.

What shipped

The Games screen — the one users spend their time in — is built and live across all three sports in both themes, delivered as seven commits over two days. The design system beneath it is implemented rather than proposed: the tokens, the card, its states and its fallbacks all describe running code. Four screens remain on the previous styling and are specified to follow.

Commercial context

The application is a Trusted Web Activity: the Android shell loads the web app at runtime, so interface changes deploy through the web pipeline and reach the Play Store app, the PWA and the browser within minutes — with no app-store review and no version bump. Every change described here is reversible in minutes, which is why the work was sequenced as seven independent commits rather than one release.

04  Foundations · ColourScoreGenius

Colour as signal, never decoration

The brand hexes are unchanged. What the system adds is contrast-corrected variants — brand green at body sizes fails accessibility standards on both grounds, so a lifted green carries text on dark and a deepened green on light.

Brand and signal

Green — lifted, text on dark#3ADE72
Green — deep, text on light#00762C
Brand orange — live only#FF7F00

Orange is reserved. It marks a live game and nothing else — never a second accent, never a warning, never decoration.

Surfaces and ink — dark

Ground#0B1016
Card#151C24
Hairline#232E38
Ink#EAF0F4
Ink secondary#8FA0AE

Neutrals carry a slight blue-green bias so they sit with the brand mark rather than beside it — a deliberate choice over default grey ramps.

Where colour is permitted

ColourPermitted useRationale
GreenThe model's output, and the app's own active chromeThe product's value is its prediction; green marks it and nothing competes
OrangeLive game state, exclusivelyRare and time-sensitive. Reserving it keeps the signal strong
NeutralsEverything else, in three ink weightsHierarchy comes from weight and contrast, not hue
No red/amber status ramp. Nothing in this product is an error a user can act on. Failures are handled by absence, not by colour.
System rule

No colour may be defined in only one theme, and no hex may be hardcoded in a component. Four violations of the first rule were found in production and are catalogued on page 13 — including one that renders a heading invisible.

04  Foundations · TypographyScoreGenius

Numbers are monospace. Words are not.

This single rule does more than any other to make the product read as instrumentation rather than a hobby app. Every figure aligns down a fifteen-card list; every label stays proportional and readable.

Cleveland Guardians

Archivo — team and player names, interface labels, headings, body copy. A grotesque with tight tracking, strong at heavy weights. Falls back to Inter Tight and the system UI stack.

+114 / −119 · 4.5 · 118.9

JetBrains Mono — scores, odds, times, percentages and all uppercase micro-labels. Tabular figures by default, so 4.5 occupies the same width as 118.9 and columns never shift. Falls back to the system monospace stack, which is available everywhere at no download cost.

Why it matters commercially

Proportional figures

Cleveland3.7
Detroit11.5
Houston118.9

Digit widths differ, so the decimal points drift and the eye has to re-find the column on every row.

Tabular monospace

Cleveland3.7
Detroit11.5
Houston118.9

Fixed digit widths plus a fixed column width. The right edge never moves — across rows, across sports, or when a basketball score crosses 100.

What changed, and why

ChangeReasoning
Split the predictionOne score per team, on that team's row. The reader learns who is favoured without arithmetic, and the numbers form a scannable column down the list.
Edge became the headlineMoved to a status rail with tier encoded in colour, border, glow and a card-edge rail. It appears on roughly two cards in fifteen — rarity earns emphasis.

Constraint respected

What the audit found here

Light mode was not being checked. Three variables — the card hover colour and two shadow definitions — were declared only inside the dark theme but consumed unconditionally, so hovering a card in light mode removed its background entirely. A fourth defect put white heading text on a near-white panel, rendering it invisible. Both are fixed in the first build commit.

Honesty constraint

The application has no live score, inning or clock data — "in progress" is inferred from the start time. The live treatment therefore shows a status and nothing more. The design deliberately avoids implying a feed the product does not have.

Sorting agrees with weight

Finished games already sorted to the bottom of the list; now they also look finished. Visual hierarchy and sort order tell the same story.

12  Build planScoreGenius

Seven commits, sequenced by risk

The work was sequenced so the first four commits were invisible in the application. Tokens, styles, helpers and components all landed without anything consuming them — leaving one high-risk commit rather than seven medium-risk ones. All seven are shipped.

What the sequence turned up

Two commits landed before the sequence that the plan had not anticipated, and both proved to be prerequisites. Four pre-existing type errors were cleared, so that "no new errors" became a meaningful check — one was a screen's core filtering silently untyped. And a linter was installed: the project carried a lint script but no configuration and no linter, so it had never run. Its first pass found five genuine defects, including a button that threw when pressed offline and chart titles that had been silently discarded, showing the wrong sport's labels.

Risk management

Commit 5 is the only change a user would notice. Because commits 1 to 4 are additive and leave no visible trace, commit 5 can still be reverted on its own — restoring the previous card while keeping the token and accessibility fixes in place. That property survives the release.

Each commit carried its own verification step. The card was checked against live production data across every state, all three sports and both themes — including a naturally occurring tied prediction, and confirmation that a covered venue fires no weather request at all.

Deployment

The Android application is a Trusted Web Activity — a thin shell loading the web app at runtime. Interface changes therefore ship through the standard web deployment and reach the Play Store app, the Microsoft Store app, the PWA and the browser simultaneously, typically within minutes.

No Android build, no version increment, no store review, and no user action required.

Scope discipline

The redesign introduced no API changes, no data-model changes and no routing changes. One backend edit was made and signed off separately: the missing indoor flag on eight covered ballparks, which had them reporting the weather outside. The only dependencies added were a linter and its plugins, which the lint script had always assumed were present.
